# 什么时候该用 WebAssembly

这是面试里最能体现**工程判断力**的一题。会用 Wasm 的人不少，
能说清"什么时候不该用"的人不多。

## 决策树

```text
你的性能瓶颈 profile 过了吗？
├─ 没有 → 先 profile。大部分"慢"其实在网络、渲染、布局，Wasm 帮不上忙
└─ 有，是 CPU 计算
   │
   ├─ 已经有成熟的 C/C++/Rust 实现？
   │  └─ 是 → ✅ 强烈推荐（移植成熟库是 Wasm 收益最确定的场景）
   │
   ├─ JS 版本充分优化过了吗？（TypedArray、避免装箱、避免多态、Worker）
   │  └─ 没有 → 先优化 JS，很多时候就够了
   │
   ├─ 数据能一次性大块传递吗？
   │  ├─ 能（图像 buffer、音频帧、文件字节） → ✅ 适合
   │  └─ 不能（需要频繁小批往返） → ❌ 边界开销会吃掉全部收益
   │
   ├─ 需要频繁操作 DOM / JS 对象吗？
   │  └─ 是 → ❌ 每次都要绕道 JS，比直接写 JS 慢
   │
   └─ 需要性能可预测（无 GC 停顿、无 deopt）吗？
      └─ 是（游戏、音频、实时协作） → ✅ 即使平均速度提升有限也值得
```

另一条完全独立的路径：

```text
需要安全执行不可信代码 / 需要语言无关的插件系统？
└─ 是 → ✅ 用 Wasm，但理由是【沙箱和能力安全】，不是性能
```

## 五个必须问的问题

### 1. 瓶颈真的是计算吗

先 profile。Performance 面板里如果 JS 执行只占 5%，剩下都是网络、
Layout、Paint、Composite，那 Wasm 一点忙都帮不上。

### 2. 数据的粒度

这是最重要的技术判据。

```js
// ❌ 细粒度：一百万次跨边界
for (let i = 0; i < 1e6; i++) sum += wasm.add(arr[i], 1);

// ✅ 粗粒度：一次跨边界
const ptr = wasm.alloc(arr.length * 4);
new Int32Array(wasm.memory.buffer, ptr, arr.length).set(arr);
const sum = wasm.sumAll(ptr, arr.length);
```

**判据**：能不能设计出一个"传大块进去、做大量工作、返回大块结果"的接口？
如果不能，Wasm 大概率不合适。

### 3. 总成本 vs 总收益

```text
收益 = (JS 执行时间 - Wasm 执行时间) × 调用次数
成本 = 下载时间 + 编译时间 + 数据编解码时间 + 跨边界开销 × 调用次数
     + 构建复杂度 + 团队学习成本 + 调试成本
```

一个 50KB 的 Wasm 模块，光下载 + 编译可能就 50~100ms。
如果它只是让一个跑 20ms 的函数变成 8ms，**总账是亏的**——除非这个函数会被调用很多次。

### 4. 团队能不能维护

Wasm 引入的不只是一个技术，是**一整条工具链**：Rust/C++ 编译环境、CI 里的交叉编译、
产物版本管理、比 JS 差得多的调试体验、更少的会改这块代码的人。

**如果只有一个人会改，那是团队风险，不是技术优势。**

### 5. 有没有更简单的替代

| 想要 | 更简单的方案 |
| --- | --- |
| 不卡主线程 | **Web Worker + Transferable**（纯 JS，零构建成本） |
| 更快的数值计算 | TypedArray + 避免装箱，或 **WebGPU compute** |
| 更快的图像处理 | Canvas 2D filter、CSS filter、**OffscreenCanvas**、WebGL |
| 更快的加解密 | **WebCrypto API**（浏览器原生实现，本来就是 C++） |
| 更快的压缩 | **CompressionStream / DecompressionStream**（原生 gzip/deflate/brotli） |

> **面试落点**：面试官问"你会用 Wasm 优化这个吗"时，
> **先反问"WebCrypto/CompressionStream/WebGPU 这些原生 API 能不能解决"**——
> 浏览器已经原生实现的东西，永远比你编译一个 Wasm 进去快、小、好维护。
> 这个反应能立刻区分出"追新技术"和"做工程"。

## 分场景速查表

| 场景 | 结论 | 理由 |
| --- | --- | --- |
| 移植 FFmpeg / SQLite / OpenCV | ✅ 强烈推荐 | 重写不现实，Wasm 是唯一路径 |
| 图像/视频编解码、压缩 | ✅ 推荐 | 计算密集 + 大块数据 + 有成熟库 |
| 游戏引擎、3D 渲染 | ✅ 推荐 | 性能可预测比峰值速度更重要 |
| 加解密、哈希 | ⚠️ 先看 WebCrypto | 原生 API 通常够用且更快 |
| 机器学习推理 | ⚠️ 先看 WebGPU/WebNN | Wasm 只在无 GPU 时是好选择；ONNX Runtime Web 两者都支持 |
| 数据可视化的数值计算 | ⚠️ 看数据量 | 小数据集 JS 够快；百万点以上才考虑 |
| 表单校验、状态管理、路由 | ❌ 不要 | 纯粹增加复杂度 |
| DOM 密集的 UI 渲染 | ❌ 不要 | 每次操作绕道 JS |
| 「用 Rust 写整个前端」 | ❌ 谨慎 | Yew/Leptos 很酷，但产物大、生态薄、招人难 |
| 服务端多租户沙箱 | ✅ 推荐 | 理由是隔离性和冷启动，不是性能 |
| 语言无关的插件系统 | ✅ 推荐 | 同上 |

## 一个务实的渐进路径

如果决定要上 Wasm，建议这样落地：

1. **先用 JS 实现并测出基线**——没有基线就没法证明 Wasm 有收益
2. **只把最热的一个函数换成 Wasm**，接口设计成粗粒度
3. **测量端到端指标**（不只是函数执行时间，要含加载 + 编译 + 编解码）
4. **保留 JS fallback**——老浏览器、Wasm 加载失败、体积预算超标时都用得上
5. 确认有收益后再扩大范围

## 面试怎么答这道题

一个高分回答的结构：

> "我会先 profile 确认瓶颈是 CPU 计算而不是网络或渲染。
> 如果是，我会看三件事：**有没有现成的原生库可以移植**、
> **接口能不能做成粗粒度的大块数据传递**、**总成本（下载+编译+编解码）
> 是不是小于节省的执行时间**。
>
> 另外我会先确认浏览器有没有原生 API 能解决——
> WebCrypto、CompressionStream、WebGPU 这些本来就是 C++ 实现的，
> 用它们比自己编一个 Wasm 更好。
>
> 还有一类场景跟性能无关：需要安全执行不可信代码，或者做语言无关的插件系统。
> 这时候用 Wasm 是为了它的**能力安全模型**——没导入的能力模块就绝对拿不到。"
