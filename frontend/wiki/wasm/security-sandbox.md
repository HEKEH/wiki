# 安全模型与沙箱

Wasm 的安全模型有**两个不同层次的目标**，混淆它们是最常见的答题失分点：

1. **保护用户**：不让恶意/有 bug 的模块逃出沙箱
2. **帮助开发者**：在目标 1 的约束内，为写出安全程序提供原语

**目标 1 是硬保证，目标 2 是尽力而为。**

## 用户侧：沙箱隔离

每个模块在与宿主运行时**故障隔离**的沙箱里执行：

- 不通过合适的 API 就无法逃出沙箱
- 除少数明确定义的情况外，执行是**确定性**的
- 受宿主的安全策略约束：浏览器里是**同源策略 + 权限策略**，非 Web 环境可能是 POSIX 模型

Wasm **本身不定义任何 API 或系统调用**——只定义 import 机制，
可用的能力完全由宿主决定。这是"能力安全（capability-based security）"的雏形：
**你没导入的东西，模块就摸不到。**

> **面试落点**：Wasm 的沙箱强度来自 **"默认零能力 + 显式导入"**。
> 一个只导入了 `console.log` 的模块，就真的只能打日志——
> 它没有任何办法凭空拿到网络、文件、DOM。这跟 JS 完全不同（JS 一上来就能摸到整个 window）。

## 开发者侧：语义层面消灭的危险

### 控制流完整性（CFI）—— 免费获得

外部控制流转移有三类，Wasm 分别用不同机制保护：

| 类型 | 边 | Wasm 的保护 |
| --- | --- | --- |
| 直接函数调用 | forward-edge | 索引必须指向 function index space 里的有效项，**加载期验证** |
| 间接函数调用 | forward-edge | `call_indirect` **运行时签名检查 + 边界检查** |
| 函数返回 | back-edge | **受保护的调用栈**，不在程序可寻址内存里 |

分支也一样：`br` 的目标必须是当前函数内有效的 label，验证期检查。

**关键在于这些保护不需要任何运行时插桩**。传统 CFI 方案要在每个调用点插入检查代码，
Wasm 靠执行语义天然拿到。

> **面试落点**：因为**代码不可变、不可观测，返回地址在保护栈上**，
> Wasm 程序天然免疫**代码注入**和**传统 ROP**（用短指令序列拼 gadget）——
> `call_indirect` 只能跳到加载期声明过的完整函数，跳不到函数中间。
> 所以 **DEP 和栈保护（SSP）这类经典缓解措施在 Wasm 里是不需要的**。

### 变量的两种落位

| C/C++ 变量 | 在 Wasm 里 | 是否受保护 |
| --- | --- | --- |
| 固定作用域的局部变量 | **local**（按索引，地址空间之外） | ✅ 溢出打不到 |
| 全局变量 | **global**（按索引） | ✅ |
| 被取地址的变量、按值返回的 struct | **线性内存里的影子栈** | ❌ 可被邻近溢出覆写 |

所以"局部变量缓冲区溢出"这类经典漏洞在 Wasm 里**部分**被消灭：
不影响 local/global，但影响线性内存里的那部分栈。

## Wasm **没有**消灭的问题

这是拉开差距的部分。

| 仍然存在的风险 | 说明 |
| --- | --- |
| **线性内存内部的越界覆写** | 边界检查只在整块内存的边界上做，**不是上下文敏感的**。模块自己的堆里，对象 A 可以覆写对象 B |
| **函数粒度的代码重用攻击** | 不能拼 gadget，但可以**篡改 table 索引，跳到另一个签名相同的完整函数** |
| **竞态 / TOCTOU** | 除了顺序执行和原子原语，Wasm 不提供调度保证 |
| **侧信道攻击** | 时间攻击等仍然可行（这也是 SharedArrayBuffer 被 COOP/COEP 锁起来的原因） |
| **源码层 UB** | Wasm 层面定义了行为，不代表 C/C++ 的 UB 消失了 |
| **资源耗尽** | 内存分配失败、栈耗尽、句柄耗尽都可能发生 |
| **业务逻辑漏洞** | 沙箱不管你的鉴权写没写对 |

> **⚠️ 常见误答**："把 C 代码编译成 Wasm 就内存安全了" ——
> **完全错误**。Wasm 保证的是"UB 不会突破沙箱"：不会执行任意代码、不会腐蚀调用栈。
> 但程序完全可以腐蚀自己的线性内存、用任意参数调 import、挂死、trap。
> **一个有堆溢出漏洞的 C 库，编译到 Wasm 后漏洞依然存在**——
> 只是利用它拿不到 RCE，最多把这个模块自己的数据搞坏。

有趣的反面推论：Wasm 里**没有 ASLR、默认不开栈 canary、堆布局高度确定**，
所以在"只污染模块自己内存"这个层面上，Wasm 里的堆溢出**比原生更容易被稳定利用**。
安全研究界对此有专门讨论（如 USENIX Security '20 的
*Everything Old is New Again: Binary Security of WebAssembly*）。

> 这一段不在 `raw/` 的源文档里，属于本库基于源文档的推论 + 业界公开研究，
> 引用时注意与"官方说法"区分开。

## 加固手段

### Clang/LLVM CFI

```bash
emcc -fsanitize=cfi ...
```

比 Wasm 内建的签名检查更细：内建检查是**Wasm 类型层面**（只有 4 个数值类型 + 引用类型），
而 LLVM CFI 在 **C++ 类型层面**做检查，语义丰富得多。

代价：每次间接调用多一次整数范围检查。未来可以用**每个签名一张 table**
（multiple indirect tables，reference-types 已提供）来消除这个开销。

### 编译期加固

```bash
-fstack-protector-strong        # 影子栈上的 canary
-D_FORTIFY_SOURCE=2
-fsanitize=address              # ASan，开发期用
```

⚠️ 这里和前面"DEP/SSP 不需要"的说法**不矛盾，但要说清楚区别**：

- 官方说 SSP 不需要，指的是**保护返回地址**这件事——返回地址在 VM 的调用栈上，
  本来就打不到，加 canary 是多余的
- 而 `-fstack-protector` 在 Wasm 上保护的是**线性内存里的那个影子栈**
  （存放被取地址的局部变量），那部分**确实会被邻近溢出覆写**

所以：**防控制流劫持不需要它，防数据被写坏需要它。**

### 部署层

- 严格 CSP：用 `'wasm-unsafe-eval'` 而不是 `'unsafe-eval'`
- 只从可信来源加载 `.wasm`，配 SRI（虽然目前对 wasm 支持不完整）
- 把不可信的 Wasm 放进独立 Worker + 独立 origin

## Trap 清单

会导致 trap（浏览器里 = `WebAssembly.RuntimeError`）的操作：

- 索引空间越界
- `call_indirect` 签名不匹配
- 调用栈耗尽（**注意：这个栈不在线性内存里**）
- 线性内存越界访问
- 非法算术：除零、`INT_MIN / -1`、有符号除法溢出、
  浮点转整数超范围（非陷阱版本 `trunc_sat` 除外）

模块自定义 trap handler 是未来工作，目前没有。

## 不确定性的完整清单

官方 Nondeterminism 文档列出的全部来源——这题问出来能筛掉 90% 候选人：

1. **不同引擎支持的 proposal 不同**（特性层面的不确定）
2. 导出函数被调用的顺序、外部传入的参数值——由宿主决定，spec 不管
3. **共享内存**上的 load / read-modify-write / wait / notify
4. **NaN 的位模式**（有约束但不完全确定；x86 和 ARM 行为就不同）
5. 无 NaN 输入却产生 NaN 时，**结果的符号位**
6. **Relaxed SIMD** 指令的结果
7. **资源耗尽**：内存分配失败、物理页分配失败、栈耗尽、句柄耗尽

设计原则是**"limited, local"**：不确定性只出现在少数明确定义的场景，
且影响是局部的——不会像 C++ 的 UB 那样让整个程序变得无意义（"nasal demons"）。

> **面试落点**：NaN 位模式不确定是因为**硬件行为本来就不统一**：
> x86 在无 NaN 输入产生 NaN 时置符号位，ARM 不置；多 NaN 输入时选哪个也不同。
> 强制规范化（canonicalize）要在每次浮点运算后加检查，开销被认为不可接受，收益又很边际。
> 这是"Wasm 在确定性和性能之间做权衡"的最佳例证。

## 为什么没有 fast-math

优化编译器常有 fast-math 开关（假设无 NaN/Inf、允许重结合）。Wasm **拒绝提供**，理由很有说服力：

**原生代码里，不确定性在开发者机器上就被解决了**——开发者能测试生成的代码，
之后行为就固定了。**Wasm 在用户侧编译**，开发者没机会测试最终行为，
不同引擎/不同版本可能表现不同。

而且大部分 fast-math 收益在**编译到 Wasm 之前**（LLVM 中端）就已经拿到了：
循环向量化、除法转乘倒数，这些在生成 Wasm 前就做完了。
