## 核心洞见

### 1. Wasm 的一切设计，都能从"沙箱 + 编译目标"这两个词推出来

这是全库最有价值的一条线索。几乎每一个"看起来别扭"的设计，追问下去都是这两个约束：

> **它是沙箱** → 函数引用不能存进线性内存（会泄露地址、能伪造跳转）
> → 所以要有 **table** + `call_indirect` 的双重检查
> → 所以返回地址放在 VM 保护的调用栈上，不在可寻址内存里
> → 所以 **天然免疫代码注入和传统 ROP**
>
> **它是编译目标** → 要快速解码、要单遍验证、要贴近硬件
> → 所以选**结构化栈机**（编码小、验证快、能流式编译）
> → 所以只有 4 个数值类型（都是 CPU 原生类型）
> → 所以没有字符串没有对象（复杂类型由源语言编译器自己拼）

面试里能把某个具体设计**倒推回这两个约束**，比背十条 API 有说服力。
见 [[wasm/core-model]]、[[wasm/security-sandbox]]。

### 2. "Wasm 比 JS 快"这句话在面试里是减分项

正确的表述分三层：

1. **加载快**是最确定的收益（二进制解码比解析 asm.js 快 ~23×，gzip 后小 20–30%）
2. **性能可预测**是被低估的收益（没有 deopt、没有 GC 停顿）——
   对游戏和音频，可预测比峰值速度更值钱
3. **稳态计算通常只有 1–3 倍**，而且跨边界密集时**可能更慢**

真正决定性能的不是"用没用 Wasm"，而是**接口粒度**：

```text
把边界画在粗粒度的地方：传大块数据 → 做大块工作 → 返回大块结果
```

一百万次 `wasm.add(a, b)` 会把所有优势吃光。见 [[wasm/performance]]。

### 3. 三条"Wasm 保护了什么"的边界必须分清

这是三档深度题的分水岭：

| | 保护 | 不保护 |
| --- | --- | --- |
| 越界 | 打不出线性内存（一定 trap） | **线性内存内部**对象互相覆写 |
| 控制流 | 免疫代码注入和传统 ROP | 函数粒度的代码重用（改 table 索引） |
| UB | UB 不会突破沙箱 | **源码层 UB 依然是 UB** |

所以 **"把 C 代码编译成 Wasm 就内存安全了"是错的**——
一个有堆溢出的 C 库编译到 Wasm 后漏洞依然存在，只是拿不到 RCE。

反直觉的推论：Wasm 里**没有 ASLR、没有栈 canary、堆布局高度确定**，
所以在"只污染自己内存"这个层面，**Wasm 里的堆溢出比原生更容易稳定利用**。
见 [[wasm/security-sandbox]]。

### 4. Wasm 3.0 的 GC 是给别人的礼物，不是给 Rust/C++ 的

一句话：**GC proposal 让 Java/Kotlin/Dart/Scala.js 这类语言不必再把整个 GC 运行时
编译进线性内存**，产物体积和与 JS 的对象互操作发生质变。

而 **Rust 和 C++ 完全不受影响**——它们本来就不用 GC，仍然用线性内存。
能主动说出这个边界，说明你不是在背新闻稿。见 [[wasm/proposals-and-versions]]。

### 5. 服务端 Wasm 的卖点不是性能，是隔离性

这条最容易被忽略，也最能拉开差距。

Wasm 实例的冷启动比容器**快好几个数量级**（厂商常引用的对比是微秒级 vs 百毫秒级，
但那高度依赖测量口径，见 [[wasm/beyond-browser]] 的说明）。加上
"**没导入的能力就绝对拿不到**"的能力安全模型——Wasm 规范里根本没有系统调用，
只有 import 机制——可以在同一进程里安全地跑成千上万个租户的代码。

这就是 Cloudflare Workers、Fastly Compute@Edge、Shopify Functions、
Envoy WasmPlugin 选它的理由。见 [[wasm/beyond-browser]]。

### 6. 工程上最贵的不是 Wasm 本身，是它带来的连锁成本

真实项目里的阻力排序（不是技术难度排序）：

1. **COOP/COEP** —— 想用多线程就要开，一开就会拦掉页面上所有没标 CORP 的
   第三方资源、并且 `window.opener` 变 null（OAuth 弹窗登录会挂）。
   **很多项目就是因为这个放弃了多线程**。
2. **构建链复杂度** —— Rust/C++ 交叉编译进 CI、产物版本管理、只有一个人会改
3. **调试体验** —— 没有 DWARF 就只能看函数索引；有 DWARF 又要装扩展、又撑大体积
4. **体积预算** —— 一个 50KB 的模块，下载 + 编译可能就 50~100ms

所以 [[analysis/when-to-use-wasm]] 里那条"**先问浏览器原生 API 能不能解决**"
（WebCrypto / CompressionStream / WebGPU）不是保守，是最高性价比的判断。

## 开放问题

**第一期留下的坑**（下次 ingest 可以补）：

1. **缺少可运行的完整 demo 项目** —— 现在的代码都是片段。
   建议补一个"图片格式转换器"的端到端例子（canvas → Wasm 编码 → 下载），
   它能一次性覆盖内存传递、零拷贝、体积优化、按需加载
2. **缺少量化性能数据** —— 现有的性能页都是定性描述 + 官方给的几个历史数字。
   应该自己跑一组 benchmark（JS vs Wasm，细粒度 vs 粗粒度接口）并记录
3. **Wasm GC 的实际用法没展开** —— 只讲了它的意义，没讲 `struct.new`/`array.get`
   这些指令怎么用，也没讲 Kotlin/Wasm 或 Dart 的实际产物长什么样
4. **Component Model 和 Wit 只提了名字** —— 如果要往服务端方向准备，这块要补
5. **调试页缺实际截图/操作流程** —— Chrome DWARF 扩展的实际体验没验证过
6. **没覆盖 AssemblyScript / Go / Zig 等其它源语言** —— 面试里偶尔会被问到
