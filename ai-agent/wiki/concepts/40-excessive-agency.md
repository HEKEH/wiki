# 过度授权（Excessive Agency）

OWASP GenAI LLM Top 10 **2026 年从更低位次升到第三**，是本次榜单最重要的排名变动。

> 投票与事故记录一致表明：**损害正落在 agentic 部署上。**

## 定义

无论 LLM 为什么出错（幻觉、prompt 设计差、模型不对齐，或直接/间接注入、被污染的工具、被攻陷的对等 agent），**只要不期望的输出能造成破坏性动作，就是 Excessive Agency**。

## 三大根因（背这三个词）

| 根因 | 典型表现 |
|---|---|
| **Excessive functionality**（功能过多） | 只需读文档，选用的第三方工具却附带修改与删除；开发期试用后弃用的工具仍然可用；开放式工具（"跑一条 shell 命令"）没有限制实际可执行范围 |
| **Excessive permissions**（权限过大） | 只读用途的工具用带 UPDATE/INSERT/DELETE 的账号连库；本该在单个用户上下文操作的工具，用一个能访问所有用户文件的高权通用身份 |
| **Excessive autonomy**（自治过度） | 删除用户文档不需要任何确认 |

在 agentic 语境下会具体表现为 OWASP Agentic 榜单的 **ASI02 工具滥用**、**ASI03 身份与权限滥用**、**ASI08 级联失败**。

## 七条根本控制

1. **最小化工具**：只给完成任务必需的工具（不需要抓 URL 就别给抓 URL 的工具）
2. **最小化工具功能**：读邮件摘要的工具就只保留读，不要带删除和发送
3. **避免开放式工具**：`run_shell`、`fetch_url` 尽量换成粒度更细的专用工具（需要写文件就做一个只能写文件的工具）；对输入参数定义严格 schema 并在使用前校验
4. **最小化工具权限**：数据库层面用只读且限表的身份，而不是靠 prompt 约束
5. **在用户上下文中执行**：跟踪用户授权与安全范围，用 OAuth 最小 scope；**在委派或多 agent 工作流中保留原始用户上下文与授权范围**，不要退化为调用方 agent 或服务身份的权限
6. **要求人工批准**：高影响动作走 HIL（[[concepts/38-human-in-the-loop]]）
7. **完全中介（complete mediation）**：**授权用代码判定，不让 LLM 决定动作是否允许**。所有对下游系统的请求都要由工具、独立的执行前策略决策点、或下游系统本身按安全策略校验。采用**分级执行（audit → warn → block → escalate）**：可逆低风险自动放行，不可逆高风险转人工

## 两条限损控制（不防止发生，但降低损害）

8. **监控工具使用**：记录并监控工具与下游系统活动
9. **限流与熔断**：对工具调用设阈值并加断路器（超阈值就停止/限流/转人工）。阈值可以是简单调用次数，也可以是**上下文感知的**（例如某参数的累计金额）

## 经典场景：被劫持的邮件助手

一个只需"读邮件做摘要"的助手，用的工具却附带发送功能，同时存在间接注入漏洞 → 恶意邮件让 LLM 扫描收件箱敏感信息并转发给攻击者。三种独立修复方式（正好对应三大根因）：

- 换成**只能读邮件**的工具（治功能过多）
- 用**只读 scope 的 OAuth**（治权限过大）
- 每封外发邮件要求用户**手动复核并点发送**（治自治过度）
- 即使都没做，对发信接口**限流**也能降低损害

## 与提示注入的关系（务必讲清）

> 提示注入是**输入侧的妥协**；过度功能、过度权限、过度自治才是让这次妥协在聊天窗之外产生后果的原因。

因此两者是"因"与"放大器"：注入无法根治，所以**必须靠限制 agency 来限制爆炸半径**。见 [[concepts/39-prompt-injection]]。
